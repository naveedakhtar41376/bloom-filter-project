# Limitations and interpretation notes

## Probabilistic interpretation

A Bloom filter does not store the original elements. It stores only a pattern of
bits generated by the hash functions. Therefore, a positive answer means
"possibly present", not "certainly present". A negative answer means
"definitely absent", provided the item would be encoded and hashed in the same
way as during insertion.

## False positives

False positives become more likely as more bits are set to 1. When the number of
inserted elements exceeds the design capacity, the empirical false-positive rate
can become much larger than the target rate. This is not a bug; it is a direct
consequence of using a fixed-size bit array.

## Duplicate insertions

The implementation counts calls to `add`. If the same item is inserted multiple
times, the bit pattern may not change after the first insertion, but
`items_added` still increases. For the project experiments we use generated
datasets with unique labels/prefixes, so this does not affect the reported
capacity experiments. In a production implementation, one would need external
state to count unique insertions exactly, but storing that state would defeat the
memory-saving purpose of a Bloom filter.

## Compression-rate interpretation

The compression experiment compares the Bloom filter's bytearray size to an
approximate Python set size. This is not a universal compression ratio for all
programming languages or storage formats. It is a practical comparison showing
how much memory is saved relative to exact membership storage in Python.

## Hash diagnostics

The hash-distribution experiment is a diagnostic, not a mathematical proof of
perfect hash independence. It checks whether hash positions are spread across
the bit array in a reasonably uniform way for several input types. The
implementation uses deterministic BLAKE2b-based double hashing to avoid Python's
process-dependent built-in hash function.
